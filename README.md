# Career Quest · NovaAI

HackAlem AI / Halyk Bank. Персональный навигатор развития: следующий грейд,
объяснимые рекомендации и личная карточка героя. Без публичных рейтингов.

## Текущий статус

Работает: профиль и рекомендации, два оформления героя, траектория, завершение
активности, история, агрегированный HR-экран, проверка и импорт четырёх файлов,
сохранение в SQLite, серверное разделение ролей, добровольный показ выбранных достижений конкретным коллегам. 96 автоматических тестов проходят;
production-сборка frontend проходит.

Добавлены интерфейс на KK/RU/EN, сигналы стагнации и AI-наставник с опциональным LLM-адаптером.
Добавлен демо-магазин Halyk Store с личным балансом и историей обменов.
Пока не реализовано: реальные награды, LMS-подтверждение обучения и SSO. Это развивающееся демо.
Точная схема официального стартового кита пока не получена.

## Запуск без Docker

После установки зависимостей (инструкция ниже) откройте `start.bat` двойным щелчком
или выполните в терминале корня проекта:

```powershell
.\start.bat
```

Дождитесь `Career Quest is ready` и откройте указанный адрес. Скрипт собирает frontend,
выбирает свободные порты и проверяет API через proxy. Уже запущенные серверы
не останавливаются. Оставьте окно открытым. Ctrl+C останавливает только этот экземпляр.
После перезагрузки компьютера запустите start.bat снова. Логи: `.runtime/*-*.log`.

Без `.env` launcher использует demo-employee / demo-hr / demo-manager.
С `.env` используются настройки из файла; переменные среды имеют приоритет.
База по умолчанию `.runtime/career-quest.sqlite3`. Чтобы продолжить предыдущий
тестовый сеанс на 5173, укажите в `.env`: `CQ_DB_PATH=.runtime/qa.sqlite3`.
Скрипт не переносит и не сбрасывает базы автоматически.

Проверка запуска и остановки: `.\.venv\Scripts\python.exe run.py --smoke`.

## Альтернатива: Docker

Нужен Docker с Compose:

```sh

```

Открыть http://localhost:8080. Токен сотрудника для локального демо: `demo-employee`.

```sh

```

Интерфейс: http://localhost:5173. Vite проксирует `/api` на backend.

## Структура

- `backend/engine.py`: чистый алгоритм ранжирования и обновления навыков.
- `backend/main.py`: FastAPI, авторизация, профиль, рекомендации, HR-агрегаты.
- `frontend/src`: React/TypeScript, адаптивное оформление на обычном CSS.
- `data`: собственный небольшой синтетический пример, НЕ официальный стартовый кит.
- `tests`: регрессионные проверки скоринга, прогресса и ролей.
- `prompts/explanation.md`: контракт будущего LLM-объяснения.

## Скоринг

Для каждого навыка события:

```
gap = max(0, required(next_grade) - current)
effective_gain = min(gap, gain, max(0, max_level - current))
p_skill = (completed_skill + 1) / (attempts_skill + 2)
p_format = (completed_format + 1) / (attempts_format + 2)
acceptance = (p_skill + p_format) / 2
score_skill = gap * effective_gain * criticality * acceptance
score_event = sum(score_skill)
```

Кандидаты фильтруются по роли, доступному приросту и факту завершения. До трёх
событий возвращаются по убыванию оценки. Равные оценки разрешаются по ID.
Сглаживание даёт 0.5 при отсутствии истории и не запрещает навык после отказов.
Оценка acceptance — эвристика, не калиброванная вероятность. История не позволяет
утверждать причины пропусков или соблюдение дедлайнов. Последний грейд использует
требования собственного уровня. Готовность — доля закрытых уровней требований,
она не гарантирует повышение.

## Проверка жюри

1. Войти с `demo-employee`.
2. Профиль E0028: System Design=2, Public Speaking=2; три пропуска/отказа Speaking.
3. Первым должен быть практикум System Design: требование Senior=4, критичность=3.
4. Раскрыть объяснение и сравнить историю/оценки альтернатив.
5. Завершить практикум: System Design станет 3. Событие исчезнет из рекомендаций.
6. Повторный POST завершения возвращает `changed=false` и не увеличивает навык.
7. Перезапуск сохраняет прогресс в SQLite. Для восстановления демо импортируйте исходные файлы из `data` через HR.

Войдите с HR-токеном `demo-hr`, выберите четыре файла из `data` и нажмите
«Проверить файлы». После предпросмотра нажмите «Заменить датасет». Замена удаляет
текущий прогресс и историю из активного датасета. Повреждённые файлы не изменяют БД.
Если данные поменялись после предпросмотра, импорт возвращает 409 и требует новой
проверки. При восстановлении исходного датасета также используйте этот сценарий.

Схема примера: employees — массив employee_id, role, grade, tenure_months, skills;
events — массив id, title, type, target_audience (роли), skill_gains;
необязательное поле mandatory (boolean, по умолчанию false) отмечает обязательное обучение;
skills — словарь ID -> requirements (грейд -> уровень), criticality (грейд -> вес).
История — CSV с заголовком employee_id,event_id,status,date (именно в этом порядке).
Все ссылки должны существовать, ID уникальны, уровни — целые 0–5, gain — 1–5,
criticality — 1–10, статусы completed/skipped/declined, дата YYYY-MM-DD.
Неизвестные поля отклоняются; файлы UTF-8, BOM допустим. Лимит комплекта — 12 MiB.
История не прибавляется к снимку навыков повторно. Официальный кит может потребовать
отдельного адаптера после получения его README.

Проверка ошибок: выставьте навык 6, повторите employee_id, добавьте ссылку на
несуществующее событие или сломайте JSON. Предпросмотр покажет путь ошибки;
исходные данные останутся доступны. Завершение активности требует expected_revision
из профиля, чтобы устаревшая вкладка не завершила событие из заменённого датасета.

## API и приватность

- GET `/api/me`, GET `/api/recommendations`: только employee.
- POST `/api/activities/{id}/complete`: только employee, идемпотентно.
- GET `/api/hr/summary`: только HR, без идентификаторов и персональных траекторий.
- GET `/api/health`: доступность приложения.

Токен передаётся через Authorization: Bearer. В демо employee-токен
привязан к EMPLOYEE_ID (по умолчанию E0028); перестановка профилей не меняет аккаунт.
Если ID отсутствует, доступ к профилю закрыт. Перед командным использованием нужны SSO,
аудит и защита агрегатов малых групп. Не загружать реальные персональные данные.
Токен интерфейса хранится только в памяти вкладки; localStorage содержит стиль и язык.

## AI-слой

Рекомендации ранжируются детерминированным скорингом. В разделе `#coach` работает
наставник: без внешнего API он объясняет факторы по шаблонам на KK/RU/EN и явно
показывает режим правил. Свободный диалог доступен через опциональный адаптер
OpenAI Responses API в `backend/coach.py`. Модель не управляет выбором рекомендаций.

GET `/api/coach/status` и POST `/api/coach` доступны только сотруднику. Сервер сам
выбирает его профиль по токену. У чата нет инструментов записи: он не может
зачесть обучение, изменить навыки, начислить Coins или открыть чужой профиль.
Защита от изменения данных обеспечена архитектурой, а не только промптом.
Текст модели всё равно может ошибаться; интерфейс показывает проверяемые факты.

Для подключения внешнего провайдера задайте на backend:

```dotenv
ALLOW_EXTERNAL_AI=true
OPENAI_MODEL=<доступная вам модель с поддержкой Responses API>
OPENAI_API_KEY=<ключ из вашей среды>
```

Compose и backend читают эти значения из корневого `.env`. Переменные среды
имеют приоритет. После изменения настроек перезапустите backend. Ключ не должен попадать во
frontend или Git. По умолчанию внешняя обработка выключена. Без всех трёх настроек
работает локальный режим. Реальный вызов модели пока не проверен: ключ не настроен.

При включении провайдер получает вопрос, до шести предыдущих сообщений и ограниченные
факторы рекомендаций. ID сотрудника и сырая история автоматически не отправляются;
введённые самим пользователем сведения остаются частью вопроса. В UI показано
предупреждение перед отправкой. Запрос использует `store=false`, без инструментов;
это не обещание полного отсутствия хранения на стороне провайдера.
[Официальная документация Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses).

Общий таймаут генерации — 8 секунд, одновременно до трёх запросов на процесс,
лимит — 20 запросов в минуту на аккаунт в одном процессе. Ошибка или таймаут дают
локальный ответ с явной отметкой. Смена ревизии данных во время ответа возвращает
409. Диалог не сохраняется в нашей БД и очищается при выходе из раздела.
Промпт чата — константа `PROMPT` в `backend/coach.py`; описание — `prompts/coach.md`.
`prompts/explanation.md` сохраняет контракт отдельного будущего LLM-объяснения карточек.

## Хранение

`backend/storage.py` сохраняет снимок в `.runtime/career-quest.sqlite3`.
Транзакции SQLite обеспечивают атомарность обновлений; ревизия предотвращает
перезапись устаревшими данными. Docker использует именованный volume `career_data`.
Переменная CQ_DB_PATH задаёт другой путь. БД исключена из Git. Удаление Docker volume
удалит сохранённый прогресс; обычный перезапуск его сохраняет.

## Добровольный показ карточки

По умолчанию карточки закрыты. В разделе «Поделиться карточкой» сотрудник задаёт
псевдоним, ID конкретных получателей и выбирает достижения. Предпросмотр ничего
не публикует. Кнопка «Разрешить показ выбранным коллегам» создаёт отдельный снимок.

Разрешённые поля: псевдоним, стиль, названия выбранных завершённых добровольных
активностей и отметка деморежима. Ни ID владельца, ни грейд, баллы, уровни навыков,
готовность к Senior, история, результаты тестов или обязательное обучение в ответ
для получателя не включаются. Новые достижения не добавляются автоматически.
Публичного каталога, рейтинга, поиска или сравнения сотрудников нет.

Ссылка требует входа выбранным аккаунтом. HR не получает права смотреть карточки.
«Отозвать доступ» закрывает серверный доступ; открытая вкладка перепроверяет доступ
каждые 10 секунд. Уже увиденное, скопированное или сохранённое получателем отозвать
технически нельзя. Замена датасета закрывает все выданные карточки автоматически.
Снимки и разрешения сохраняются в SQLite; максимум 20 активных карточек на владельца.

### Демонстрация для жюри

1. Войти с `demo-employee`, завершить практикум в деморежиме.
2. В «Поделиться карточкой» указать E0029 и выбрать практикум.
3. Проверить предпросмотр и разрешить показ.
4. Открыть ссылку в новой вкладке, войти с `demo-colleague`.
5. Видны только выбранный образ и достижение, без навыков и грейда.
6. В первой вкладке отозвать доступ; получатель теряет доступ при следующей проверке.
7. Токен HR и неизвестный токен не дают доступ к этой карточке.

В Docker аккаунт E0029 — демонстрационный получатель без собственного профиля
в маленьком датасете; он может открыть только адресованную ему карточку.
EMPLOYEE_ACCOUNTS_JSON на backend задаёт соответствие токен -> employee_id.
Это временный механизм демоавторизации, не SSO. Токены не передаются в URL и
не сохраняются в localStorage. Все демонстрационные токены заменяются перед
публичным развёртыванием.

### Подтверждение обучения и правила хакатона

Самостоятельное завершение выключено по умолчанию. DEMO_MODE=true явно включает
кнопку «Демо: отметить выполненным». Docker Compose включает её для защиты проекта;
это не подтверждение обучения LMS. Снятие флага закрывает POST завершения на сервере.
Интеграция LMS и отдельный процесс проверяющего пока не реализованы.

Обязательное обучение отмечается mandatory=true и не доступно для показа коллегам.
Баллов за него нет; демо-Coins начисляются только за добровольное закрытие разрывов.
Сотрудник не обязан открывать карточку и не получает награды за публичность.
AI-чат читает только разрешённый контекст,
без инструментов начисления навыков, Coins, подтверждения или отмены обучения.

Функция обмена карточками реализует согласованную модель приватности, однако
финальное соответствие трактовке правил остаётся за организаторами хакатона.

## Служебный доступ HR и руководителя

HR видит ID, роль и грейд сотрудников в демоорганизации, наличие следующего шага,
причину отсутствия рекомендации и статусы обязательного обучения. Руководитель
видит те же служебные поля только по ID из серверной настройки MANAGER_ACCOUNTS_JSON.
Она не меняется при импорте датасета и не управляется браузером. Пустой список
означает отсутствие доступа. Прямой запрос чужого ID возвращает 404.

В Compose добавлен токен `demo-manager` с доступом только к E0028. Для запуска
вручную задайте перед стартом backend:

```powershell
$env:MANAGER_ACCOUNTS_JSON='{"demo-manager":["E0028"]}'
```

GET `/api/hr/employees` и `/api/hr/employees/{employee_id}` возвращают только
служебную проекцию. Уровни навыков, добровольная история, карточки, чат и личные
предпочтения не раскрываются. `/api/hr/summary` также ограничен командой руководителя.
Импорт остаётся только у HR. HR-токен демо имеет доступ ко всей демоорганизации;
подразделения HR и организационная структура SSO пока не реализованы.

Статус «требования выполнены» означает отсутствие разрывов по навыкам, а не
решение о повышении. «Нужно дополнить каталог» означает, что разрыв есть, но
доступного события нет. Это не оценка вовлечённости и не прогноз увольнения.

Обязательное событие имеет mandatory=true, аудиторию target_audience и опциональный
срок due_date в формате YYYY-MM-DD. На этом этапе назначение определяется ролью,
срок один на событие. Если завершение есть в истории, статус completed;
иначе прошедший срок даёт overdue, остальные случаи pending. Повторная периодическая
сертификация, индивидуальные назначения, оценки тестов и LMS пока не реализованы.
Исходный маленький датасет не содержит обязательных курсов, поэтому пустой блок
показывает «Нет назначений». Их можно добавить через HR-импорт.

Проверки этапа: 53 теста, включая изоляцию команд, прямой доступ по ID, пустую
команду, отсутствие приватных полей, сроки и причины отсутствия рекомендаций;
production-сборка Vite проходит.

## Обновлённый кабинет сотрудника

Пять экранов переключаются через боковую навигацию и URL hash:
`#overview` — цель, персональная карточка, сводка и рекомендации;
`#character` — выбор аниме/футбола, навыки, достижения и добровольный показ карточки;
`#career` — траектория, объяснения, обязательное обучение и история;
`#coach` — персональный наставник и факты рекомендаций.
Кнопки «назад/вперёд» браузера поддерживаются. Персонажи — оригинальные
векторные изображения; новые профессиональные достижения берутся из backend.
Графические стили не меняют навыки. Процент обозначает готовность по требованиям,
а не общий рейтинг сотрудника. `#store` — демо-магазин, личный баланс и история обменов.

Интерфейс проверен в браузере на обычной ширине и мобильном экране 390px:
навигация, переключение стиля и отображение карьеры. Используются адаптивные сетки,
фокус для клавиатуры и отключение анимаций при prefers-reduced-motion.
Production-сборка проходит. Backend на этом этапе не изменялся.

## Қазақша / Русский / English

Переключатель языка доступен над экраном входа и во всех кабинетах. Выбор сохраняется
в localStorage (`cq-language`), атрибут html lang обновляется. `translations.json`
содержит переводы интерфейса; `i18n.ts` переводит отображаемые строки, не изменяя
входные данные и отправляемые на сервер значения. Три названия демонстрационных
курсов переведены. Неизвестные названия внешнего датасета, технические ID/названия
навыков и подробные ошибки валидации отображаются в исходном виде. Переводы внешних
курсов потребуют каталога переводов из стартового кита. Казахские тексты перед
защитой желательно вычитать носителю языка. Название грейда не меняет смысл при
смене языка. LLM для перевода персональных данных не используется.

## Сигналы стагнации и помощь в один клик

В HR/manager-кабинете появился фильтр «Сотрудники в зоне стагнации» с объяснением
причины. Это воспроизводимая эвристика, не прогноз attrition, не оценка намерений
человека и не основание для кадровых санкций. Ограничение команды сохраняется.

- Более 6 календарных месяцев с последнего завершения: строго раньше даты,
  отстоящей на 6 месяцев назад. Ровно 6 месяцев не срабатывает.
- Если завершений нет, сигнал ставится только при наличии собственной истории
  старше 6 месяцев и tenure_months >= 6; иначе показывается недостаток данных.
- Три или более подряд skipped среди явно отмеченных рекомендаций. В CSV разрешена
  необязательная пятая колонка `recommended`, значения строго true/false.
  Исходный четырёхколоночный CSV совместим и НЕ считается журналом рекомендаций.
  Declined и completed прерывают серию рекомендаций. При противоречивых статусах
  в один день серия консервативно прерывается; будущие записи не учитываются.

Результат в `/api/hr/employees` включает только флаги/причины и признаки достаточности
истории, без персональной истории и оценок навыков. Кнопка «Сформировать предложение»
вызывает POST `/api/hr/employees/{id}/support-proposal`. Возвращаются подходящие
активности, целевой грейд и область запроса на ментора. Это черновик по скорингу,
ничего не отправляется, не назначается и не изменяется в профиле. Каталог менторов
ещё не подключён; система не выдумывает человека. LLM-инсайтов пока нет.

Для демонстрации импортируйте четыре файла из `examples/stagnation` через HR.
По состоянию на 2026-09-23 E0028 имеет старое завершение и три явно отмеченных
пропуска рекомендаций. Импорт заменяет текущий набор данных, прогресс и закрывает
выданные карточки; для восстановления импортируйте исходные четыре файла из `data`.

Проверено: 61 backend-тест, production-сборка, переключение KK/RU/EN, сохранение
языка после reload, HR-фильтр и персональное предложение в браузере.


## Halyk Store: личные демо-награды

Три категории: «Для работы», «Для себя», «Для семьи и детей». Семейные награды
включают кино, мастер-класс и аквапарк. Все цены условные; настоящий сертификат,
заказ или банковский бонус не создаются. Баланс и история доступны только владельцу,
не HR, руководителю или получателю карточки. Нет публичного рейтинга.

За первое завершение добровольной активности начисляется:

```
Coins = 100 * sum(min(gap_before, event_gain, max(0, max_level-current)))
```

Учитываются только разрывы относительно следующего грейда. Обязательное событие
всегда даёт 0 Coins. Демо-завершение и демо-обмен разрешены только при DEMO_MODE=true.
До интеграции LMS это имитация подтверждения, а не проверенное обучение.
Импортированная история и завершения до появления магазина не дают Coins задним числом.
Начальный баланс — 0. Цель Senior Ready сама по себе пока не даёт отдельной награды.

API: GET `/api/store`, POST `/api/store/redeem` (employee only). Клиент передаёт
item_id, request_id (UUID) и expected_epoch; цену и владельца определяет сервер.
Повтор запроса с тем же UUID не списывает повторно, тот же UUID для другого товара
отклоняется. BEGIN IMMEDIATE в SQLite предотвращает одновременную трату одного
баланса. Начисление сохраняется атомарно с навыками и историей; повторное завершение
не награждается. Журнал сохраняется в таблице coins. UI показывает последние 100
операций; баланс вычисляется по всему журналу.

Импорт нового датасета очищает демо-баланс и журнал обменов и меняет epoch.
Старые открытые формы после импорта получают 409. В HR-предпросмотре показано
предупреждение. Это политика демонстрационной среды; реальные кошельки нельзя
сбрасывать таким способом.

### Как показать магазин жюри

1. На свежем датасете войти с demo-employee и завершить System Design в деморежиме.
2. Открыть Halyk Store: баланс 100 Coins, в истории +100 за system-lab.
3. Выбрать книгу за 100, проверить сумму и подтвердить демо-обмен.
4. Баланс 0, в истории списание; товары недоступны при нехватке Coins.
5. Проверить категории и языки KK/RU/EN. Обязательные события не дают награды.

13 новых тестов магазина плюс предыдущие 76: всего 89. Проверены параллельное
списание, повтор запроса, импорт, сохранение, роли и отсутствие наград за mandatory.
В браузере проверена цепочка завершение → +100 → обмен → 0 и семейная категория
на казахском. Production-сборка проходит. Реальные награды и внешняя LLM не тестировались.

### Без Docker и при занятом порте

Docker не обязателен. Используйте раздел запуска выше. Если сервер уже запущен,
не запускайте второй экземпляр на том же порте. Для отдельного запуска можно выбрать
другую пару портов (например, backend 8010 и frontend 5174):

```powershell
# Терминал 1, корень проекта; сначала задайте токены и DEMO_MODE как в инструкции выше
.\.venv\Scripts\python -m uvicorn backend.main:app --host 127.0.0.1 --port 8010
```

```powershell
# Терминал 2
cd frontend
$env:CQ_API_TARGET="http://127.0.0.1:8010"
pnpm dev --port 5174 --strictPort
```

CQ_API_TARGET должен указывать на фактический порт backend. При обновлении кода
перезапустите backend; если запущен vite preview, пересоберите frontend (`pnpm build`).


## Настройка AI через .env

1. Скопируйте `.env.example` в `.env`, если файла ещё нет.
2. Откройте `.env` в редакторе и самостоятельно вставьте ключ в OPENAI_API_KEY.
3. Укажите OPENAI_MODEL — ID доступной вашему API-проекту модели с поддержкой Responses.
4. Установите ALLOW_EXTERNAL_AI=true, чтобы разрешить внешнюю обработку.
5. Перезапустите приложение. Статус «LLM настроена — доступ проверяется при запросе»
   означает наличие настроек, но не подтверждает работоспособность ключа.
6. Отправьте вопрос. Успешный внешний ответ имеет отметку LLM; при ошибке или
   таймауте показывается явно обозначенный резервный ответ по правилам.

Ключ не вводится в UI и не добавляется в Git. Launcher не передаёт API-ключ и токены
процессам frontend. `.env` исключён из Git. Без настроек приложение работает локально.
[Официальная документация OpenAI](https://developers.openai.com/api/docs/guides/production-best-practices).

Формат `.env`: одна строка KEY=value, необязательные парные кавычки, пустые строки
и комментарии на отдельных строках. BOM допустим. Интерполяция, исполнение команд
и многострочные значения не поддерживаются. Ошибка сообщает номер строки без её содержимого.

Проверки: 96 тестов, сборка, запуск frontend/backend, API через proxy и остановка
после --smoke. Настоящий OpenAI API не вызывался: ключ и модель пока не настроены.
