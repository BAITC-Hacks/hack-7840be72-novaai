# Career Quest · NovaAI

HackAlem AI / Halyk Bank. Персональный навигатор развития: следующий грейд,
объяснимые рекомендации и личная карточка героя. Без публичных рейтингов.

## Текущий статус

Работает: профиль и рекомендации, два оформления героя, траектория, завершение
активности, история, агрегированный HR-экран, проверка и импорт четырёх файлов,
сохранение в SQLite, серверное разделение ролей, добровольный показ выбранных достижений конкретным коллегам. 53 автоматических теста проходит;
production-сборка frontend проходит.

Пока не реализовано: LLM-чат, реальные иллюстрации персонажей, магазин наград,
LMS-подтверждение обучения, полноценная локализация и SSO. Это развивающееся демо.
Точная схема официального стартового кита пока не получена.

## Запуск одной командой

Нужен Docker с Compose:

```sh
docker compose up --build
```

Открыть http://localhost:8080. Токен сотрудника для локального демо: `demo-employee`.
HR-токен: `demo-hr`. Порт опубликован только на loopback. Для изменения токенов
скопируйте `.env.example` в `.env`. Не используйте демо-токены для публичного сервера.
Docker в среде автора не установлен; сборка контейнеров требует отдельной проверки.

Для разработки без Docker: Python 3.12+, Node 22+, pnpm 11.

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r backend/requirements.txt
$env:EMPLOYEE_TOKEN="demo-employee"
$env:HR_TOKEN="demo-hr"
$env:DEMO_MODE="true"
$env:EMPLOYEE_ACCOUNTS_JSON='{"demo-colleague":"E0029"}'
.\.venv\Scripts\python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Во втором терминале:

```sh
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

Интерфейс: http://localhost:5173. Vite проксирует `/api` на backend.

## Структура

- `backend/engine.py`: чистый алгоритм ранжирования и обновления навыков.
- `backend/main.py`: FastAPI, авторизация, профиль, рекомендации, HR-агрегаты.
- `frontend/src`: React/TypeScript, адаптивное оформление на обычном CSS.
- `data`: собственный небольшой синтетический пример, НЕ официальный стартовый кит.
- `tests`: регрессионные проверки скоринга, прогресса и ролей.
- `prompts/explanation.md`: контракт будущего LLM-объяснения.

## Скоринг

Для каждого навыка события:

```
gap = max(0, required(next_grade) - current)
effective_gain = min(gap, gain, max(0, max_level - current))
p_skill = (completed_skill + 1) / (attempts_skill + 2)
p_format = (completed_format + 1) / (attempts_format + 2)
acceptance = (p_skill + p_format) / 2
score_skill = gap * effective_gain * criticality * acceptance
score_event = sum(score_skill)
```

Кандидаты фильтруются по роли, доступному приросту и факту завершения. До трёх
событий возвращаются по убыванию оценки. Равные оценки разрешаются по ID.
Сглаживание даёт 0.5 при отсутствии истории и не запрещает навык после отказов.
Оценка acceptance — эвристика, не калиброванная вероятность. История не позволяет
утверждать причины пропусков или соблюдение дедлайнов. Последний грейд использует
требования собственного уровня. Готовность — доля закрытых уровней требований,
она не гарантирует повышение.

## Проверка жюри

1. Войти с `demo-employee`.
2. Профиль E0028: System Design=2, Public Speaking=2; три пропуска/отказа Speaking.
3. Первым должен быть практикум System Design: требование Senior=4, критичность=3.
4. Раскрыть объяснение и сравнить историю/оценки альтернатив.
5. Завершить практикум: System Design станет 3. Событие исчезнет из рекомендаций.
6. Повторный POST завершения возвращает `changed=false` и не увеличивает навык.
7. Перезапуск сохраняет прогресс в SQLite. Для восстановления демо импортируйте исходные файлы из `data` через HR.

Войдите с HR-токеном `demo-hr`, выберите четыре файла из `data` и нажмите
«Проверить файлы». После предпросмотра нажмите «Заменить датасет». Замена удаляет
текущий прогресс и историю из активного датасета. Повреждённые файлы не изменяют БД.
Если данные поменялись после предпросмотра, импорт возвращает 409 и требует новой
проверки. При восстановлении исходного датасета также используйте этот сценарий.

Схема примера: employees — массив employee_id, role, grade, tenure_months, skills;
events — массив id, title, type, target_audience (роли), skill_gains;
необязательное поле mandatory (boolean, по умолчанию false) отмечает обязательное обучение;
skills — словарь ID -> requirements (грейд -> уровень), criticality (грейд -> вес).
История — CSV с заголовком employee_id,event_id,status,date (именно в этом порядке).
Все ссылки должны существовать, ID уникальны, уровни — целые 0–5, gain — 1–5,
criticality — 1–10, статусы completed/skipped/declined, дата YYYY-MM-DD.
Неизвестные поля отклоняются; файлы UTF-8, BOM допустим. Лимит комплекта — 12 MiB.
История не прибавляется к снимку навыков повторно. Официальный кит может потребовать
отдельного адаптера после получения его README.

Проверка ошибок: выставьте навык 6, повторите employee_id, добавьте ссылку на
несуществующее событие или сломайте JSON. Предпросмотр покажет путь ошибки;
исходные данные останутся доступны. Завершение активности требует expected_revision
из профиля, чтобы устаревшая вкладка не завершила событие из заменённого датасета.

## API и приватность

- GET `/api/me`, GET `/api/recommendations`: только employee.
- POST `/api/activities/{id}/complete`: только employee, идемпотентно.
- GET `/api/hr/summary`: только HR, без идентификаторов и персональных траекторий.
- GET `/api/health`: доступность приложения.

Токен передаётся через Authorization: Bearer. В демо employee-токен
привязан к EMPLOYEE_ID (по умолчанию E0028); перестановка профилей не меняет аккаунт.
Если ID отсутствует, доступ к профилю закрыт. Перед командным использованием нужны SSO,
аудит и защита агрегатов малых групп. Не загружать реальные персональные данные.
Токен интерфейса хранится только в памяти вкладки; localStorage содержит лишь стиль.

## AI-слой

Сейчас объяснения строятся детерминированно из факторов, это явно обозначено в UI.
LLM пока не подключена. Будущий адаптер получает только факторы, не меняет выбор
алгоритма, ограничивается таймаутом 8 секунд и возвращается к шаблону при ошибке.
Промпт находится в `prompts/explanation.md`. Внешним сервисам данные не передаются.


Цели задержки из ТЗ: UI <2с, рекомендации <10с. Нагрузочный замер на полном

## Хранение

`backend/storage.py` сохраняет снимок в `.runtime/career-quest.sqlite3`.
Транзакции SQLite обеспечивают атомарность обновлений; ревизия предотвращает
перезапись устаревшими данными. Docker использует именованный volume `career_data`.
Переменная CQ_DB_PATH задаёт другой путь. БД исключена из Git. Удаление Docker volume
удалит сохранённый прогресс; обычный перезапуск его сохраняет.

## Добровольный показ карточки

По умолчанию карточки закрыты. В разделе «Поделиться карточкой» сотрудник задаёт
псевдоним, ID конкретных получателей и выбирает достижения. Предпросмотр ничего
не публикует. Кнопка «Разрешить показ выбранным коллегам» создаёт отдельный снимок.

Разрешённые поля: псевдоним, стиль, названия выбранных завершённых добровольных
активностей и отметка деморежима. Ни ID владельца, ни грейд, баллы, уровни навыков,
готовность к Senior, история, результаты тестов или обязательное обучение в ответ
для получателя не включаются. Новые достижения не добавляются автоматически.
Публичного каталога, рейтинга, поиска или сравнения сотрудников нет.

Ссылка требует входа выбранным аккаунтом. HR не получает права смотреть карточки.
«Отозвать доступ» закрывает серверный доступ; открытая вкладка перепроверяет доступ
каждые 10 секунд. Уже увиденное, скопированное или сохранённое получателем отозвать
технически нельзя. Замена датасета закрывает все выданные карточки автоматически.
Снимки и разрешения сохраняются в SQLite; максимум 20 активных карточек на владельца.

### Демонстрация для жюри

1. Войти с `demo-employee`, завершить практикум в деморежиме.
2. В «Поделиться карточкой» указать E0029 и выбрать практикум.
3. Проверить предпросмотр и разрешить показ.
4. Открыть ссылку в новой вкладке, войти с `demo-colleague`.
5. Видны только выбранный образ и достижение, без навыков и грейда.
6. В первой вкладке отозвать доступ; получатель теряет доступ при следующей проверке.
7. Токен HR и неизвестный токен не дают доступ к этой карточке.

В Docker аккаунт E0029 — демонстрационный получатель без собственного профиля
в маленьком датасете; он может открыть только адресованную ему карточку.
EMPLOYEE_ACCOUNTS_JSON на backend задаёт соответствие токен -> employee_id.
Это временный механизм демоавторизации, не SSO. Токены не передаются в URL и
не сохраняются в localStorage. Все демонстрационные токены заменяются перед
публичным развёртыванием.

### Подтверждение обучения и правила хакатона

Самостоятельное завершение выключено по умолчанию. DEMO_MODE=true явно включает
кнопку «Демо: отметить выполненным». Docker Compose включает её для защиты проекта;
это не подтверждение обучения LMS. Снятие флага закрывает POST завершения на сервере.
Интеграция LMS и отдельный процесс проверяющего пока не реализованы.

Обязательное обучение отмечается mandatory=true и не доступно для показа коллегам.
Баллов за него нет; магазина и начисления Coins в этой версии ещё нет.
Сотрудник не обязан открывать карточку и не получает награды за публичность.
AI-чат пока не подключён; планируемый чат будет только читать разрешённый контекст,
без инструментов начисления навыков, Coins, подтверждения или отмены обучения.

Функция обмена карточками реализует согласованную модель приватности, однако
финальное соответствие трактовке правил остаётся за организаторами хакатона.

## Служебный доступ HR и руководителя

HR видит ID, роль и грейд сотрудников в демоорганизации, наличие следующего шага,
причину отсутствия рекомендации и статусы обязательного обучения. Руководитель
видит те же служебные поля только по ID из серверной настройки MANAGER_ACCOUNTS_JSON.
Она не меняется при импорте датасета и не управляется браузером. Пустой список
означает отсутствие доступа. Прямой запрос чужого ID возвращает 404.

В Compose добавлен токен `demo-manager` с доступом только к E0028. Для запуска
вручную задайте перед стартом backend:

```powershell
$env:MANAGER_ACCOUNTS_JSON='{"demo-manager":["E0028"]}'
```

GET `/api/hr/employees` и `/api/hr/employees/{employee_id}` возвращают только
служебную проекцию. Уровни навыков, добровольная история, карточки, чат и личные
предпочтения не раскрываются. `/api/hr/summary` также ограничен командой руководителя.
Импорт остаётся только у HR. HR-токен демо имеет доступ ко всей демоорганизации;
подразделения HR и организационная структура SSO пока не реализованы.

Статус «требования выполнены» означает отсутствие разрывов по навыкам, а не
решение о повышении. «Нужно дополнить каталог» означает, что разрыв есть, но
доступного события нет. Это не оценка вовлечённости и не прогноз увольнения.

Обязательное событие имеет mandatory=true, аудиторию target_audience и опциональный
срок due_date в формате YYYY-MM-DD. На этом этапе назначение определяется ролью,
срок один на событие. Если завершение есть в истории, статус completed;
иначе прошедший срок даёт overdue, остальные случаи pending. Повторная периодическая
сертификация, индивидуальные назначения, оценки тестов и LMS пока не реализованы.
Исходный маленький датасет не содержит обязательных курсов, поэтому пустой блок
показывает «Нет назначений». Их можно добавить через HR-импорт.

Проверки этапа: 53 теста, включая изоляцию команд, прямой доступ по ID, пустую
команду, отсутствие приватных полей, сроки и причины отсутствия рекомендаций;
production-сборка Vite проходит.
